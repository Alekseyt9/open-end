# Warp-решатель

Экспериментальный GPU-backend физики `ecology-2`. Реализованы все 17 инструкций VM, копирование кода и памяти с мутациями, консервативный перенос, зарядка химии, связи, рождение/распад, оба SplitMix64 RNG и применение с откатом скомпилированных DSL-модулей.

Для запуска здесь использован уже установленный Python: `F:/src/game_arc/.venv-warp/Scripts/python.exe`, Warp 1.15.0, RTX 5070. В другом окружении зависимости перечислены в `requirements.txt`.

## Запуск из корня репозитория

```powershell
& F:/src/game_arc/.venv-warp/Scripts/python.exe warp-sim/run.py --snapshots data/dsl-split.json --ticks 1250 --output data/warp-result.json
```

Можно передать несколько снимков после `--snapshots`: они должны иметь одинаковые физические параметры, кроме seed. Перед исполнением снимки проверяются существующим Go-загрузчиком. `--fixture` вместо `--snapshots` принимает пакет `initial` из результатов `cmd/warp-reference` или бенчмарка. Для проверки входа требуется Go; исходный проект ARC не меняется и пакеты в его окружении не переустанавливаются.

Результат `warp-physical-report-1` содержит физическое состояние, глобальные счётчики, оба RNG и состояние DSL. **Это не Go snapshot:** исторические журналы `genomes`/`origins`, их SHA-256 и накопленные показатели по каждому геному на GPU не строятся. Нельзя передавать отчёт в `cmd/sim -load` или считать его `physical_sha256` равным хешу полного Go-снимка. Исходные журналы не подменяются выдуманной историей. Для дальнейших шагов внутри Python можно многократно вызывать `Batch.run` на одном экземпляре; массивы между вызовами остаются на устройстве.

Ограничения первого backend: сетка и настройки одинаковы внутри пакета; аргументы VM в диапазоне `[-2^30, 2^30)`; исходные tick/ID меньше `2^62`; оценочный объём основных массивов ограничен 6 GiB. Стандартные и мутировавшие программы проекта помещаются в эти ограничения. Внешняя интерактивная установка модулей пока остаётся Go API; Warp исполняет замороженное расписание из снимка.

## Сравнение скорости

```powershell
& F:/src/game_arc/.venv-warp/Scripts/python.exe warp-sim/benchmark.py --worlds 1,16,96,256 --size 32 --ticks 1000 --warmup 300 --repeats 3 --workers 16 --scenario ecology --output data/warp-benchmark-repeat
```

Каталог вывода должен быть новым. Перед измерением мира выполняется 300 тиков Go, затем CPU и GPU начинают с одинакового состояния. CPU использует настоящий `kernel.Step`, а не Python-аналог; измеряются 1 и 16 рабочих потоков. Начальная подготовка, загрузка снимков и финальная сериализация исключены из CPU-времени. Go продолжает вести штатные исторические журналы.

Для Warp отдельно записаны прогретое время решения с синхронизацией после каждой порции тиков, время с подготовкой массива/передачами/выгрузкой физического состояния и время начальной загрузки/компиляции модуля. Холодный JIT не включается в прогретое ускорение. `warp_end_to_end_seconds` также включает Python-подготовку и проверки инвариантов, но не сериализацию итогового отчёта в JSON. Это сравнение работающего Go-ядра с экспериментальным backend, выполняющим меньше работы наблюдателя; преимущество Warp, если оно появится, не означает ускорение полного Go-пайплайна.

Каждый повтор сверяет все клетки, частицы (ID, родитель, код, память, IP, цель, возраст/поколение), связи, оба RNG, глобальный accounting и DSL-журнал. Совпадение требуется точное, без допусков. Сводка содержит все измерения, медианы и хеши исходников/начальных и конечных состояний. Частичный или не прошедший сверку прогон помечается `failed`.

Сценарии: `ecology` — стандартные мутации 1%; `mutation` — стресс с 10%; `baseline` — мир без химии; `assay` — смесь двух выделенных линий без мутаций; `dsl` — смена на тике 100 и откат на 200; `odd` — неравные размеры сетки и интервалы переноса. Для проверки смен DSL задавайте `--warmup 0`, чтобы обе смены попали в измеряемые шаги.

## Исполнение и проверки

Порядок разрешения конфликтов и условных вызовов RNG остаётся последовательным внутри мира. Свободные слоты частиц переиспользуются, отдельный список сохраняет сортировку по ID и циклический сдвиг. Новая частица исполняется со следующего тика, обслуживание оплачивает уже в текущем.

По умолчанию `--lanes 32`: отдельный CUDA warp на мир, активна одна lane. Это уменьшает влияние разных ветвлений миров друг на друга. `--lanes 1` упаковывает соседние миры в одну группу; в пилоте это оказалось значительно медленнее. `--chunk 8` ограничивает длительность одного запуска на GPU, обслуживающей также дисплей. Синхронизация включена в замеры. Это реализация через [NVIDIA Warp](https://nvidia.github.io/warp/), а не распараллеливание конфликтующих действий внутри одного мира.

```powershell
& F:/src/game_arc/.venv-warp/Scripts/python.exe -m unittest discover -s warp-sim -p test_solver.py -v
go test ./...
go vet ./...
```

Дифференциальные тесты включают все опкоды, энергетическое голодание, мутации, нечётную сетку с разными интервалами переноса, смесь со связями и повторным использованием слотов, DSL и разбиение запуска на разные порции. Для Warp CPU можно задать `WARP_TEST_DEVICE=cpu`; это отдельный backend Warp, не Go-эталон бенчмарка.
